# Mutation authority journal (foundation)

This package is a local journal for a **single NAS mutation gateway**. It does not enforce H-8 by itself. The custody-only gateway uses it for immutable uploads; no current NFS, FUSE, farm, import, WebDAV, or administrative writer is routed through it. A gateway must become the only holder of backend write credentials and writable handles, then admit every mutation through this package. The journal owns one whole-volume session/epoch at a time; separate media and derivative namespaces are not exempt.

`Claim` persists an owner and monotonically increasing epoch. Each live process enforces admission with a monotonic deadline; the stored wall timestamp is informational. Observed expiry durably latches `admission_closed`, even when unsettled work denies a successor, so wall-clock rollback cannot revive it. `Open` conservatively closes admission for all prior owners because their monotonic deadline cannot survive restart. Any claim after closure, including the same session, gets a successor epoch only after every prior `PREPARED` row is explicitly reconciled. The same session may renew its epoch during one process only while its lease remains live. `Execute` persists the immutable operation ID, digest, expected revision, session, and epoch **before** calling the trusted backend. It does not hold the journal mutex or a SQLite transaction during the callback. An identical retry after `COMMITTED` returns the exact stored receipt while its epoch remains current, even after lease expiry; a changed request or old epoch is refused. Callback error, cancellation, missing durability proof, or failed receipt write leaves `PREPARED` and forbids automatic replay. `ResolveCommitted` and `ResolveNoEffect` are trusted reconciliation APIs, not client endpoints. `NO_EFFECT` requires positive evidence that the old effect did not occur and cannot still occur.

The gateway must hash a canonical request that covers operation type, payload identity, destination/object identity, and expected parent/object revisions; preserve immutable upload bytes; validate preconditions under its sole mutation authority; and generate stable backend evidence for the exact operation. A committed receipt proves only the durable outcome of that typed effect plus this journal's durable commit. For media publication this requires independent proof of both JuiceFS metadata and object durability. A private immutable upload stage is a distinct custody effect and cannot prove media publication or retire a spool row. A successful callback, client ack, FUSE close, path match, or size match is insufficient. Before a successor starts, the gateway must fence retained descriptors, subprocesses, backend sessions, and credentials. It must also retain/reconcile an effect that can survive a gateway process crash. The journal's fixed directory `flock` rejects another cooperating process; symlink/hardlink aliases are refused or canonicalized. It cannot fence a rogue process or a child retaining write capability. The gateway must provision a private local directory and sync its entry through the ancestor chain **before** `Open`; `Open` refuses an absent parent and syncs its own DB/lock/WAL entries. Put one database in that directory; never delete or replace `.mutationauthority.lock` while a gateway may run.

`Renew` extends only an exact live epoch, without creating or advancing an owner. `ListPrepared` provides bounded, deterministic startup reconciliation; it never filters on operation type. A gateway must examine every returned row and refuse unknown kinds. The custody-only executable uses a fresh, marked state directory and an enforced custody namespace. Before it can admit media operations, that same whole-volume journal needs an explicit migration to persisted operation kinds; an independent media journal would violate the ownership boundary.

The gateway should offer a receipt-consumer interface to the spool publisher. A spool row may retire its exact mirror/index/reservation generation only after consuming a matching **media publication** receipt. The generic journal receipt must remain private to trusted adapters. Offline bytes and punched stages remain custody until a fresh epoch explicitly re-admits them; this package never republishes them. Cross-process credential isolation, mounted JuiceFS durability, restart fencing, and current H-8 RED oracles remain integration and acceptance gates.

For an in-process backend with unjoinable writers, `BeginBackendProcess` consumes
one initialization attempt and irreversibly pins this same journal until OS
process exit. `PinProcessLifetime` can install that lifetime constraint before a
trusted backend constructor runs. Strong process-global ownership prevents GC
from releasing the lock after constructor failure. `Close` returns
`ErrProcessLifetime`; it cannot be used to hand over authority early. A durable
`BackendProcess` record precedes creation of each new runtime worker identity.
These records do not settle PREPARED operations or grant media authority. The
custody-only executable does not attach this backend component yet.

Journal schema version 2 persists an explicit operation kind and media file incarnation alongside the immutable digest and predecessor token. A new database is initialized transactionally; recognized pre-versioned schemas migrate without replaying or settling any operation. Unknown schema objects, changed constraints, unsupported versions, or invalid persisted identities are refused. The historical core schema and its optional backend-process/configuration additions are recognized explicitly. Generic legacy operations retain their opaque meaning. A media publication identity requires a nonempty opaque file incarnation and complete predecessor token; the trusted gateway must bind all relevant object/parent preconditions and any absent-version token in its canonical request. These journal fields do not establish backend durability or authorize spool retirement.

Custody startup classifies legacy requests only under closed admission, with no active callback or started backend. Every request across all states must validate before a single transaction assigns the custody kind. A crash between schema migration and classification leaves legacy requests for a later startup to inspect; missing or partial custody artifacts remain uncertain.

`ExecuteStage` atomically records a bounded canonical media intent alongside PREPARED before any SDK effect. Its inode binding, allocated slice IDs, and every raw object attempt remain in the same journal. Closure refuses unwritten slices or unverified attempts and permanently closes raw upload admission under the same journal lock. Even a closed stage stays PREPARED and produces no receipt. Version 1 journals migrate without adopting historical operations as stages. Custody-only startup still refuses media rows; recovery and settlement require a separately qualified trusted adapter.

Generic `Execute`, `ResolveCommitted`, and `ResolveNoEffect` refuse media publication operations until a qualified publication/recovery adapter exists. Historical typed media rows remain inspectable, but generic evidence cannot issue a media receipt or unblock succession. Custody and legacy operations retain their existing settlement behavior.

Schema version 3 adds `media_retention` without rebuilding the referenced operations table. A trusted SDK may certify confinement of every preexisting PREPARED media stage only after its current process completes the Redis takeover and validates exact stage/backend identity. The certificate binds the observed snapshot, backend digest, Redis run ID and recorded worker generation; it does not settle the operation. Claim exempts only stages certified by this process, using an in-memory generation latch that resets on every Open. A late provider request may still create its recorded object. No media receipt, NO_EFFECT outcome, publication, replay or spool retirement follows from retention. All other PREPARED work continues to block succession.
